问题 1（紧急）：编辑内容丢失
═══════════════════════════════════════

用户现象：
- 打开便签，输入了文字。
- 点返回箭头回列表页。
- 再打开这条便签，发现刚才输入的文字**没保存**，内容还是旧的。
- 概率性发生，不是每次都丢。

背景：v1.5.5 把 autosave 从"立即"改成"延迟 450ms"（在 blur 事件里）。

排查方向：
1. 找到 blur 事件处理函数（约 L4553-4559）：
   clearTimeout(saveTimer);
   saveTimer = setTimeout(autosave, 450);
2. 追踪 autosave 函数：
   a. 它从哪里读编辑器内容？
   b. 它写到哪个 note 对象的哪个字段？
   c. 它用哪个 id 写 IndexedDB？
3. 追踪返回路径：
   a. 点返回箭头时，除了 blur 事件，还触发了什么？
   b. backToList() 里有没有 clearTimeout(saveTimer) 的操作？
   c. 有没有地方会覆盖 saveTimer 变量？
4. 追踪延迟的卡片更新（L3530-3611）：
   a. 它读的 note 内容是"编辑器里的最新内容"还是"旧的 note 对象"？
   b. 如果读的是旧 note 对象，那是不是 autosave 还没执行，note 对象就是旧的？
5. 关键问题：
   a. 从"用户在编辑器里打字"到"IndexedDB 里存了新内容"，
      完整的数据流是什么？
   b. blur 时启动的 450ms 定时器，如果在 450ms 内用户又做了别的操作
      （比如切换到另一条便签、点返回、再次进入编辑），这个定时器会被清除吗？
   c. 如果定时器被清除，这次编辑是不是就彻底丢了？

必须明确回答：
- 用户在编辑器输入后，多久之内数据是"只在内存里、还没落库"的？
- 在这段时间内，哪些操作会导致数据丢失？
- 1.5.5 的"延迟 450ms"是否引入了丢失窗口？

修复方向（供参考）：
- **立即更新内存中的 note 对象**（title / content / updatedAt），
  不要等 autosave。这样即使 IndexedDB 还没写，内存里已经是新内容。
- **再异步写 IndexedDB**：用 setTimeout(0) 或 requestIdleCallback 写，
  不阻塞 UI，也不丢数据。
- 或者：**返回时同步写 IndexedDB**，但把写操作放在动画启动之后的
  微任务里（queueMicrotask），让动画先跑起来。
- 关键：不能让"数据落库"依赖一个可能被清除的定时器。

═══════════════════════════════════════
问题 2：编辑后返回仍然卡顿
═══════════════════════════════════════

用户现象：
- 编辑便签后，点返回箭头回列表页。
- 编辑页的滑出动画仍然卡顿。
- 列表页也卡、闪。
- 1.5.5 已经"把 DOM 更新延迟到动画后"，但没效果。

这说明卡顿的根因**不是 DOM 更新**，而是别的东西。重新排查：

排查方向：
1. **编辑器本身的开销**：
   a. 编辑页滑出时，contenteditable 是否还在被浏览器当作"活动编辑区"？
   b. 滑出时编辑器里的图片（<img>）是否在重新解码？
   c. 滑出前是否应该先把编辑器设为 contenteditable="false" 或 blur，
      让浏览器停止文本布局计算？
2. **.no-blur 的移除时机**：
   a. 1.5.5 说 .no-blur 在 t≈400ms 移除。
   b. 移除瞬间，列表页 26 处 backdrop-filter 同时恢复，
      可能产生重绘尖峰。
   c. 检查：能否分批恢复？或者先恢复顶栏、胶囊，再恢复卡片？
   d. 或者：.no-blur 根本不加在列表页上？
3. **列表页卡片的布局重算**：
   a. 返回时，如果列表页的卡片因为"编辑后的卡片位置变了"而重排，
      触发其他卡片的 transition。
   b. 检查是否有卡片的位置动画（FLIP 或 transform）在返回时执行。
4. **编辑页的子元素**：
   a. .editor-panel、.editor-bar、.editor-toolbar 都有 backdrop-filter。
   b. 滑出时这些玻璃层每帧都在重新计算 backdrop。
   c. 检查：滑出期间能否临时关闭这些子元素的 backdrop-filter？
5. **contenteditable 的历史栈**：
   a. 如果 undo/redo 栈在滑出时还被处理，会有开销。
   b. 检查 undo/redo 栈是否在滑出时被清空或序列化。

必须明确回答：
- 1.5.5 的"延迟 DOM 更新"是否真的执行到了？
  （用 console.log 或断点验证）
- 卡顿发生在滑出动画的哪个阶段？
  （首帧？中段？尾段？）
- 编辑前 vs 编辑后，滑出期间有哪些代码路径不同？

修复方向（供参考）：
- 滑出开始时立即 editorEl.blur() + 移除 contenteditable 属性，
  减少浏览器文本布局开销。
- .no-blur 的恢复分批执行（用 requestAnimationFrame 分两帧恢复）。
- 检查滑出期间是否有其他 CSS transition 被触发。
