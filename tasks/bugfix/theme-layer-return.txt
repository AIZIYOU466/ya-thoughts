Bug 1：主题圆形覆盖的图层位置错误
═══════════════════════════════════════

当前现象：
- 圆形覆盖动画从屏幕上层覆盖整个页面，包括卡片在内的一切内容。
- 用户希望：这个覆盖只影响最底层的背景层（卡片下面那一层），不影响卡片本身。

用户原话："覆盖的动画不要影响到其他的，只影响到最底层的背景。比如说有卡片那一层，覆盖动画就影响卡片下面那一层，不要从最顶层覆盖全局。"

要求：
1. 找到 #theme-ripple 覆盖层的 HTML 和 CSS。
2. 检查它的 z-index 值。如果是最顶层（比如 9999），说明它覆盖了所有内容。
3. 检查页面各层的 z-index 关系：
   - 页面背景层（body 或 #app 的背景）
   - 卡片列表容器（#list-view）
   - 卡片本身（.note-item）
   - 编辑页（#editor-view）
   - 各种弹层（toast、确认框、菜单）
4. 明确回答：
   a. 覆盖层的当前 z-index 是多少？
   b. 应该改成多少，才能"只覆盖背景层、不覆盖卡片"？
   c. 覆盖动画进行时，卡片应该保持什么状态（旧主题还是新主题）？

修复方向：
- 覆盖层的 z-index 降到**背景层之上、卡片之下**。
- 覆盖层只填充纯色（新主题的背景色 var(--bg-page)）。
- 圆扩散时，用户看到的是背景在变，卡片保持不动。
- 覆盖完成那一帧，切换 data-theme，让卡片的颜色也跟着切换（瞬间切换，不做动画，避免闪帧）。

Bug 2：主题切换的取色方向反了
═══════════════════════════════════════

当前现象：
- 无论是"明亮→暗色"还是"暗色→明亮"，圆形覆盖的取色都用同一套逻辑（暗色到亮色的方向）。
- 用户希望：明亮→暗色时，覆盖层用明亮模式的取色来扩散，覆盖完成后变成暗色。

用户原话："从明亮覆盖成暗色模式，这个时候应该是明亮模式的取色来圆形覆盖，现在这个主题转换取色都用的从暗色到亮色的那个，要优化。"

要求：
1. 找到主题切换按钮的 click 处理函数。
2. 检查覆盖层的填充色是从哪个 CSS 变量或常量取的。
3. 检查：切换前和切换后，覆盖层的颜色分别是怎样计算的？
4. 明确回答：
   a. 明亮→暗色时，覆盖层当前用的什么颜色？
   b. 暗色→明亮时，覆盖层当前用的什么颜色？
   c. 两个方向是否用了相同的颜色逻辑？

修复方向（推荐）：
- 覆盖层的颜色 = 切换前主题的**背景色**（旧主题色）。
- 圆从触点扩散时，用户看到的是旧主题色在扩大，覆盖住整个屏幕。
- 覆盖完成那一帧，切换 data-theme（页面变成新主题色），移除覆盖层。
- 这样两个方向的视觉效果都会正确：
  · 明亮→暗色：白色圆从触点扩散，扩散完成后页面变成暗色。
  · 暗色→明亮：暗色圆从触点扩散，扩散完成后页面变成明亮。

**但如果用户希望的是"覆盖层用新主题色扩散"**（即圆内是新主题，圆外是旧主题），那就在圆扩散完成前，圆内始终保持新主题色，圆心在触点位置。

请先确认当前实现是哪种，然后按"覆盖层用旧主题背景色"的方式修正。

Bug 3：主题覆盖动画结束时闪帧
═══════════════════════════════════════

当前现象：
- 圆形覆盖扩散到全屏时，有一瞬间的重加载感或闪帧。

要求：
1. 检查覆盖完成时的处理流程：
   a. 设置 data-theme
   b. 移除覆盖层
   c. 是否还有其他操作（比如重新渲染、切换视图）？
2. 检查是否有以下操作：
   - innerHTML 重建任何容器
   - classList 的批量修改
   - style 属性的读写触发了重排
3. 检查时序：设置 data-theme 和移除覆盖层之间是否有 requestAnimationFrame 或 setTimeout 分隔？

修复方向（参考 motion-web 的 "no flash" 规范）：
- 覆盖完成的那一帧，按这个顺序执行：
  1. 设置 data-theme（触发主题切换）
  2. 强制浏览器重排一次：void document.documentElement.offsetHeight
  3. 在同一个 requestAnimationFrame 回调里移除覆盖层
- 整个过程中，不要重建任何 DOM。
- 不要有 setTimeout 分隔（会导致中间帧露出旧主题）。
- 用双 rAF 包裹，确保移除覆盖层发生在下一帧渲染之前。

Bug 4：点软件自身的返回箭头触发重加载
═══════════════════════════════════════

当前现象：
- 在便签编辑页，点软件自身的返回箭头（左上角的 "<"）→ 会触发整页重加载、闪动，右下角 + 按钮也会闪。
- 但用手机系统手势返回（从屏幕边缘向内滑）→ 不会触发重加载，过渡平滑。
- 说明：两条返回路径走了不同的逻辑。

要求（systematic-debugging 流程）：
1. 找到编辑页左上角返回箭头的 HTML 和 click 处理函数。
2. 找到 Android 返回键（backButton）的处理函数（应该是 Capacitor App 插件的 addListener）。
3. 对比两个函数：
   a. 它们是否都调用了同一个 backToList()？
   b. 如果不是，分别调用的是什么？
   c. backToList() 内部做了哪些 DOM 操作（renderList、切换 class、清除 inline style 等）？
4. 检查：
   a. 点返回箭头时，编辑器是否有未提交的 input 或 blur 事件触发了额外操作？
   b. 点返回箭头时，是否有 e.preventDefault() 之外的默认行为被触发？
   c. 手机手势返回时，是不是走的更"干净"的路径（只调 backToList 不触发其他）？

修复方向：
- 让两条路径**调用完全相同的返回逻辑**。
- 如果手势返回走的路径更干净，就把返回箭头的 click 处理改为调用同一个函数。
- 如果 backToList 内部有"重建列表 DOM"的操作，改成"只更新必要部分"。
- 返回过程中，不做任何 innerHTML 重建，只做：
  · 编辑页 classList.remove('active')
  · 列表页 classList.add('active')
  · 更新数据（如果编辑器有未保存内容）
