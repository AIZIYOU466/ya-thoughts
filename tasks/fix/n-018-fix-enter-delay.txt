═══════════════════════════════════════
现象
═══════════════════════════════════════

从列表页进入编辑页时：
- 编辑页从右侧滑入（动画正常）。
- 但列表页在编辑页完全覆盖屏幕后**还保持可见一段时间**，才消失。
- 用户观感："我都进入编辑页过了多少毫秒了，列表页才消失。"
- 看起来像列表页"慢一拍"才隐藏。

注意：这是**新出现的问题**，可能是上一轮修复"返回闪蓝底"时引入的副作用
（当时为了让返回时列表页提前可见，可能也影响了进入时的隐藏时机）。

═══════════════════════════════════════
根因排查（systematic-debugging 流程）
═══════════════════════════════════════

按以下顺序检查：

1. **找到 show('editor') 函数**（或类似的进入编辑页函数）。
2. 逐行读它的执行流程：
   a. 什么时候 listView.classList.remove('active') 或 visibility: hidden？
   b. 是在编辑页滑入动画**开始前**、**进行中**、还是**结束后**？
   c. 是否有 setTimeout / transitionend 延迟了列表页的隐藏？
3. 检查是否有以下模式（错误的）：
   a. 编辑页滑入动画 320ms，列表页在动画结束后才隐藏 → 那列表页会多显示 320ms
   b. 有个 setTimeout(() => listView.remove('active'), 320) → 延迟了隐藏
   c. 列表页的 transition 也在 320ms 后才生效 → 双重延迟
4. 检查 CSS 中 #list-view 的 transition 属性：
   a. 如果 #list-view 有 transition: visibility 320ms，那么
      classList.remove('active') 后，visibility 会在 320ms 后才真正变成 hidden。
   b. 这就是"列表页慢一拍"的根因。
5. 检查上一轮修复"返回闪蓝底"时，是否为了提前显示列表页，把列表页的
   visibility 切换也加了 transition。

关键问题：
- 进入编辑页时，列表页是"立即隐藏"还是"渐变隐藏"？
- 如果是"渐变隐藏"，那用户就会看到列表页在编辑页滑入后慢慢消失——这就是现象。

═══════════════════════════════════════
修复方向
═══════════════════════════════════════

正确的行为应该是：

【进入编辑页时】
- 编辑页开始滑入的**同一帧**，列表页保持可见（用户能看到编辑页从右侧盖过来）。
- 编辑页滑入完成后（320ms 后），列表页**立即**隐藏（visibility: hidden，无过渡）。
- 用户感知：编辑页盖满屏幕后，列表页"啪"地消失，不应该有延迟。

【返回列表页时】
- 编辑页开始滑出的**同一帧**，列表页立即可见（用户能看到编辑页向右滑走，露出列表）。
- 这正是上一轮修复"闪蓝底"的效果，必须保留。

修复方案：

1. 检查 #list-view 的 transition 属性：
   - 如果有 transition: visibility 之类的，**删掉**。
   - visibility 的切换不应该有过渡，应该是瞬时的。

2. 检查 show('editor') 里列表页隐藏的时机：
   - 应该在编辑页滑入完成后**立即**隐藏，不是延迟 +320ms。
   - 用 transitionend 事件：编辑页滑入动画结束 → 立即 listView.classList.remove('active')。
   - 或者更简单：编辑页滑入完成时用 setTimeout(320)，但要在动画结束时立刻执行。

3. 如果发现当前实现是"列表页有 visibility transition"，删掉 transition，改为瞬间切换。

4. 检查是否有双重延迟：
   - 比如编辑页动画结束 → setTimeout(100) → 再隐藏列表页。
   - 这种多余延迟要删。
