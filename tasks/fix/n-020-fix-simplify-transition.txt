问题 1：简化转场动画
═══════════════════════════════════════

用户决定：从列表页到编辑页，只保留编辑页从右侧滑入的动画。
去掉之前加的"列表页被推开"（左移 + 缩放 + 变暗）的动画。

理由：用户觉得两个页面同时动的效果反而没那么丝滑，
希望更简单直接——编辑页从右侧盖过来，列表页保持不动。

具体操作：
1. 删除 #list-view 的 transition 属性（transform 和 opacity 的 320ms 过渡）。
2. 删除 #list-view 的 transform-origin。
3. 删除 #list-view.pushed 相关的 CSS 规则。
4. 删除 JS 里 showEditor / hideEditorWithTransition 中给 listView 加/删
   .pushed 类的逻辑。
5. 保留编辑页的滑入/滑出动画（translateX(100%) ↔ translateX(0)）。
6. 保留 #list-view 的 visibility 切换逻辑（编辑页打开期间隐藏，返回时显示）。
7. 保留 .no-blur 冻结逻辑。
8. 保留 will-change 的动态挂载。

目标：编辑页从右侧滑入，列表页保持不动，编辑页盖住列表页后列表页隐藏。
返回时相反：编辑页向右滑出，列表页从下层显现。

问题 2：编辑文本后返回列表页有卡顿和闪烁
═══════════════════════════════════════

用户现象：
- 编辑文本后（无论是新建还是编辑已有），退出到列表页，
- 有一个小的卡顿过程。
- 同时有一个闪烁，集中在列表中上部（可能跟加载新编辑的卡片有关）。
- 只编辑了文本，没有改图片，闪烁仍然出现。

排查方向（systematic-debugging 流程）：

1. **找到编辑页保存/返回时的逻辑：**
   a. 编辑内容变化时，autosave 函数做了什么？
   b. 返回列表页时，backToList() 做了什么？
   c. 是否调用了 renderList() 全量重建整个列表？

2. **检查 renderList() 的行为：**
   a. 是否 listEl.innerHTML = '' 然后逐条重建所有卡片？
   b. 每次重建卡片时，是否重新测量摘要高度、重新查询星标状态？
   c. 如果是，那就是卡顿的根源——全量重建开销大，且会闪烁。

3. **检查"列表中上部闪烁"的具体位置：**
   a. 是新编辑的卡片被移除后重新插入？
   b. 还是所有卡片都重新渲染了一遍？
   c. 闪烁是白屏、闪烁一下、还是闪烁多次？

4. **检查是否有重复渲染：**
   a. 返回时是否既触发了 renderList，又触发了其他更新逻辑？
   b. 是否有两次渲染叠加，导致闪烁？

5. **检查卡片的入场动画：**
   a. 卡片是否有 fade-in / pop-in 之类的入场动画？
   b. 如果每次重建卡片都触发入场动画，视觉上就是"闪烁"。

预期根因（供参考）：
- 编辑后返回，backToList() 调用了 renderList() 全量重建。
- renderList 里每张卡片都用 createElement + 插入，插入瞬间触发 CSS 动画。
- 或者：新编辑的卡片从列表中间被移除、重新插入到正确位置（按时间排序）。
- 闪烁集中在"列表中上部"，说明新编辑的卡片被重新排序到了顶部附近。

修复方向：
1. **定向更新，不重建：**
   - 返回列表时，找到被编辑的那张卡片（用 note.id 查 li[data-id]）。
   - 只更新这张卡的标题、摘要、时间戳（textContent 级）。
   - 如果排序变了（因为 updatedAt 更新，卡片要移到顶部）：
     · 用 transform 动画把它平滑移动过去，或者
     · 先移除再插入到新位置，但加 CSS 动画淡入。
   - 不动其他卡片。

2. **避免全量 renderList：**
   - 只在列表结构真的变化（新增、删除、切换分段/搜索）时调用 renderList。
   - 编辑内容后的返回，走"定向更新"路径。

3. **禁用重建时的入场动画：**
   - 如果确实需要重建，先加一个 .no-anim 类给列表容器，
     让所有卡片的入场动画禁用，重建完再移除。
   - 避免"每次重建都闪一下"。

4. **检查是否有重复调用：**
   - 用 console.log 打印 renderList 被调用的次数和时机。
   - 如果返回时调用了 2 次以上，说明有冗余调用。
